# Training a policy (Stage 2), and plugging in your own

Two halves. The first is `stage2_train_bc.py`, the built-in behaviour-cloning path: it turns
stage 1's `demo.hdf5` into a trained checkpoint in one command. The second is the contract an
**external** method — diffusion policy, ACT, anything you write yourself — has to satisfy so
that `stage3_evaluate.py` can score it. You do not have to use stage 2 to be evaluated; you do
have to match the observation/action interface in [The policy contract](#the-policy-contract).

```bash
MUJOCO_GL=egl python stage2_train_bc.py --dataset ~/demos_4bin/demo.hdf5
```

`MUJOCO_GL=egl` is needed because training runs offscreen rollouts. See [1_install.md](1_install.md).

## What that one command does

Stage 2 is a wrapper around four robomimic steps. Each is skipped if its output already exists,
so re-running is cheap; `--overwrite` forces the first three to redo.

| # | Step | Detail |
| --- | --- | --- |
| 1 | `env_args` patch | robomimic reads `data.attrs["env_args"]`; stage 1 writes `env_info`. Derived and added in place if missing ([stage2:80](../pick_place_4bin/stage2_train_bc.py#L80)) |
| 2 | Observation extraction | `demo.hdf5` → `demo_low_dim.hdf5`. Replays every recorded simulator state and records observations from it ([stage2:47](../pick_place_4bin/stage2_train_bc.py#L47)) |
| 3 | Train/val split | writes `mask/train` and `mask/valid` into the converted file; 10% validation by default |
| 4 | Training | builds a robomimic `bc` config and calls `robomimic.scripts.train.train` |

Step 2 is the one worth understanding. **Stage 1 stores no observations** — only raw simulator
states (see [2_teleoperation.md](2_teleoperation.md)). The observation vector is regenerated by
replaying those states, which means changing the observation set later is a re-extraction, not a
re-collection. It also means the extraction is deterministic: the same `demo.hdf5` always yields
the same `demo_low_dim.hdf5`.

### The converted dataset

```
data (attrs: env_args, total)
├── mask/train, mask/valid              demo names in each split
└── demo_N (attrs: model_file, num_samples, camera_info)
    ├── obs/object                (T, 14)   <- the four keys stage 2 trains on
    ├── obs/robot0_eef_pos        (T, 3)
    ├── obs/robot0_eef_quat       (T, 4)
    ├── obs/robot0_gripper_qpos   (T, 2)
    ├── obs/robot0_joint_pos      (T, 7)    <- extracted too, unused by stage 2
    ├── obs/robot0_eef_vel_lin    (T, 3)       (also *_vel_ang, joint_pos_cos/sin,
    ├── obs/robot0_gripper_qvel   (T, 2)        joint_vel -- 11 keys in total)
    ├── actions                   (T, 7)
    ├── states                    (T, 71)   carried over from stage 1
    ├── rewards                   (T,)      sparse unless --shaped
    └── dones                     (T,)      1 wherever the success check passes
```

This file is also the natural input for an external method: it is a plain hdf5, and nothing about
it is robomimic-specific except the `mask` groups.

One thing does **not** survive the conversion: the per-demo `target_bin_id` attribute that stage 1
writes is not copied into the converted file. The commanded compartment lives only inside the
observation there — `obs/object[t][-4:]`, identical at every `t` of a demo.

## The three presets

All three are behaviour cloning; `--algo` picks one.

| `--algo` | Architecture | When it is the right choice |
| --- | --- | --- |
| `rnn` (default) | LSTM (2×400) + deterministic MSE head | Demos from one operator or a script. The action distribution is effectively unimodal, and the LSTM supplies the phase information (approaching vs. already grasped) that a single observation does not carry |
| `mlp` | 2×1024 feed-forward + MSE | Fast, and a useful floor to compare against. Without history it plateaus early on this task |
| `rnn_gmm` | LSTM + Gaussian-mixture head | Genuinely multimodal demos — several operators solving the task different ways |

Two notes on `rnn_gmm`, both learned the hard way ([stage2:18](../pick_place_4bin/stage2_train_bc.py#L18)):
`gmm.min_std` is raised to 0.02 from robomimic's 1e-4, because the OSC rotation dimensions are
constant in this data and a mixture fitting a zero-variance dimension drives its std to the floor
and blows up the gradients; and robomimic re-samples the mixture component at every evaluation
step, so an unconfident policy produces visibly jittery actions.

## The policy contract

This is the part that matters for any method, built-in or not. It is fixed by the environment,
not by robomimic.

### Observation

`stage3_evaluate.py` hands the policy a **dict of numpy arrays**, one entry per observable. The
four keys stage 2 trains on:

| Key | Shape | Contents |
| --- | --- | --- |
| `object` | (14,) | see the breakdown below |
| `robot0_eef_pos` | (3,) | end-effector position, world frame |
| `robot0_eef_quat` | (4,) | end-effector orientation, xyzw |
| `robot0_gripper_qpos` | (2,) | the two finger joints |

23 dimensions in total. `object` decomposes as:

| Slice | Shape | Contents |
| --- | --- | --- |
| `object[0:3]` | (3,) | Can position, world frame |
| `object[3:7]` | (4,) | Can orientation, xyzw |
| `object[7:10]` | (3,) | Can position **relative to the end-effector** |
| `object[10:14]` | (4,) | **target compartment, one-hot** |

`object[-4:]` is the whole task specification. It is the only thing that differs between "put the
can in the back-left bin" and "put it in the front-right bin", so a policy that ignores it cannot
do better than chance on the conditioning:

```python
target_bin = int(np.argmax(obs["object"][-4:]))     # 0-3
```

The dict actually carries more than these four keys — `robot0_joint_pos`, `robot0_eef_vel_lin`,
`robot0_gripper_qvel` and others are all present at evaluation time. You may use them. Stage 2
does not, and if you train on them you must be able to produce them at evaluation, which you can.

### Action

`np.ndarray` of shape **(7,)**, consumed by an `OSC_POSE` controller at **20 Hz**:

| Index | Meaning | Range |
| --- | --- | --- |
| 0-2 | end-effector position delta, `dx dy dz` | [-1, 1] → ±5 cm per step |
| 3-5 | orientation delta, axis-angle `drx dry drz` | [-1, 1] |
| 6 | gripper | < 0 opens, > 0 closes |

These are **deltas from the current pose**, not absolute targets. The controller clips each
dimension to [-1, 1] and rescales to ±0.05 m, so an action of 2.0 and an action of 1.0 do exactly
the same thing.

> **Gotchas for anything that normalizes actions.** Keyboard-teleoperated actions do not look
> like the [-1, 1] continuous values the interface suggests. Measured over the demos collected so
> far:
>
> | | `dx` | `dy` | `dz` | `drx` `dry` `drz` | gripper |
> | --- | --- | --- | --- | --- | --- |
> | range | ±3.75 | ±7.5 | -3.75 … 7.5 | **0** | ±1 |
> | fraction exactly 0 | 97.6% | 92.9% | 94.9% | 100% | 0% |
> | values in (0, 1] | none | none | none | — | — |
>
> Three consequences:
>
> 1. **The position channels are bang-bang, not continuous.** A key is either held or it is not,
>    so each axis is 0 or a saturating step; 95% of all position entries are exactly zero. There
>    is nothing in between. An MSE-regressed policy averages across that gap and outputs a smeared
>    intermediate value — which is one of the reasons a distributional method (GMM, diffusion) is
>    worth trying here in the first place.
> 2. **The stored magnitude is not the executed magnitude.** The controller clips every dimension
>    to [-1, 1] before rescaling to ±5 cm, so ±3.75 and ±7.5 move the arm *identically*. The
>    dataset encodes a distinction the simulator ignores. Clip the actions to [-1, 1] as the first
>    thing your loader does — that is the action the robot actually took, and it collapses the
>    spurious two-level structure into a clean {0, ±1}. Do it **before** computing normalization
>    statistics, not after.
> 3. **Three action dimensions have zero variance.** No rotation was ever commanded, so `drx`,
>    `dry` and `drz` are identically 0. Min-max or mean-std normalization divides by
>    `max - min = 0` on those dimensions: implementations that do not guard with an epsilon
>    produce NaN, and those that do produce a dimension of pure noise. Either drop the rotation
>    dimensions and emit zeros for them at evaluation, or hard-code the normalizer to pass them
>    through.
>
> Percentiles do not help here — the 99th percentile of `|dy|` is 7.5, the saturating value
> itself. Clipping is the correct fix, not a robust-statistics one.

### How the policy is called

The evaluator's side of the contract — the `make_policy` entry point, the `start_episode()` hook,
the one-observation-in-one-action-out loop, and a worked adapter for a chunked, history-conditioned
policy — is in
[4_evaluation.md](4_evaluation.md#evaluating-an-external-checkpoint---policy). Two things to know
while you are still training:

- Your policy will be asked for **one action per step**, with no history handed to it, so a method
  needing observation history or action chunks must buffer them internally.
- Keep the observation key order identical between training and evaluation. Nothing checks it, and
  a permuted vector fails silently.

## Outputs

robomimic writes one timestamped run directory per training run:

```
trained_models/bc_rnn_4bin/<timestamp>/
├── config.json
├── logs/            tensorboard event files, plus a text log
├── models/          model_epoch_<N>.pth, and model_epoch_<N>_..._success_<rate>.pth
└── videos/          rollout renders from the periodic evaluations
```

Checkpoints are saved every 100 epochs and whenever rollout success improves. Stage 2 prints the
best one and the exact stage 3 command to evaluate it:

```bash
MUJOCO_GL=egl python stage3_evaluate.py --agent trained_models/bc_rnn_4bin/<timestamp>/models/<best>.pth --all-bins
```

Training-time rollouts (25 every 50 epochs) sample the target bin at random. That success rate is
not the number to report — see [4_evaluation.md](4_evaluation.md).

## Options

| Flag | Default | Meaning |
| --- | --- | --- |
| `--dataset` | *required* | stage 1's `demo.hdf5`, or an already-converted dataset |
| `--algo` | `rnn` | `rnn`, `mlp` or `rnn_gmm` |
| `--epochs` | 600 | LR decays ×0.3 at 65% and 90% of this |
| `--output-dir` | `./trained_models` | run directories go here |
| `--name` | `bc_<algo>_4bin` | experiment name |
| `--rollout-n` / `--rollout-rate` | 25 / 50 | rollouts per evaluation, and how often to evaluate |
| `--val-ratio` | 0.1 | validation fraction |
| `--seed` | 1 | training seed |
| `--converted` | *derived* | path for the observation-extracted dataset |
| `--overwrite` | off | redo extraction and split |

## When it fails

| Symptom | Cause | Fix |
| --- | --- | --- |
| `num_samples=0`, raised deep in the dataloader | The validation split rounded to zero demos: robomimic takes `int(val_ratio * n_demos)`, which is 0 for anything under 10 demos at the default 10% | Handled, see [Small datasets](#small-datasets-10-or-fewer-demos) below. If you hit it in your own tooling, raise `--val-ratio` |
| `training demonstrations overlap with validation demonstrations!` | robomimic refuses to let one demo appear in both filter keys | Handled — the mirrors stage 2 creates have distinct names |
| `WARNING: model directory already exists! overwrite? (y/n)` then `EOFError` | robomimic prompts interactively when a run directory of the same name exists, and there is no stdin to answer it | Pass a fresh `--name`, delete the old run directory, or run in a real terminal |
| `EGLError: EGL_NOT_INITIALIZED` in a `__del__` traceback **after** training finished | Teardown noise from the offscreen renderer being freed at interpreter exit | Harmless; ignore it. Check for the checkpoint path in the output — if it printed, the run succeeded |

## Small datasets (10 or fewer demos)

Holding a demo out of a 4-demo dataset costs 25% of the data to measure almost nothing, and at
the default `--val-ratio 0.1` robomimic's `int(0.1 × 4) = 0` produces an empty validation set that
fails deep in the dataloader. So at or below **10 demos** stage 2 stops holding anything out and
**validates on the training demos**:

```
[stage 2] WARNING: 4 demos is not enough to hold out a validation set (need more than 10).
[stage 2] WARNING: validating on the TRAINING demos - train and valid are the same data, so the
                   validation loss measures fit, not generalisation. Ignore it.
[stage 2] all 4 demos mirrored into the valid split; validating on the training data
```

Training and evaluation are otherwise completely normal. Only the validation loss changes meaning:
it now measures how well the policy fits the data it was trained on, so it falls steadily and tells
you nothing about generalisation. **The rollout success rate is the only honest signal on a dataset
this small.**

How it works, in case you look inside the file: robomimic asserts the two filter keys name disjoint
demos, so stage 2 mirrors each demo under a second name — `demo_1` also appears as `demo_100001` —
and points `mask/valid` at the mirrors. These are HDF5 **hard links**, one trajectory under two
names, so nothing is copied and the file does not grow. Only the converted `demo_low_dim.hdf5` is
touched, never stage 1's `demo.hdf5`. Once the dataset grows past 10 demos the mirrors are removed
automatically and a real split takes over.

Collect more data as soon as you can. The default `--episodes-per-bin 10` gives 40 demos, which
splits normally.

## Before you read too much into the numbers

- **Bin balance.** Stage 1 keeps collecting until every compartment has its quota, so a dataset it
  finished is balanced. A dataset assembled from an interrupted run is not, and a policy trained on
  bin-0-heavy data learns to drive to bin 0 and score 25% on `--all-bins`. Check the balance
  before blaming the architecture — `demo.hdf5` carries `target_bin_id` as a per-demo attribute,
  and the converted file only as `obs/object[0][-4:]`.
- **Duplicate demos.** Identical trajectories land in both the train and validation splits, which
  makes the validation loss meaningless.
- **Tiny datasets.** At or below 10 demos there is no held-out data at all — see
  [Small datasets](#small-datasets-10-or-fewer-demos). 4 demos trains and evaluates cleanly and tells you
  almost nothing.
- **Validation loss is not success rate.** On this task they decorrelate early. The rollout success
  rate from the periodic evaluations is the number to watch.
